## Authentication and first-time account flow — 7 October 2026

- Root cause: the React callback explicitly exchanged a code that `@supabase/ssr`'s browser client already exchanged automatically. This explained an established session followed by a consumed/missing-verifier error. Replace the callback page with a request-scoped SSR route; it is the sole code-exchange owner and returns all SDK cookies on its redirect. Browser/server clients use the same project/key and the SDK's standard PKCE storage, with no custom verifier mechanism.
- Add Next.js 15 refresh middleware with complete request/response cookie propagation. It excludes the callback and forwards legacy Site URL code redirects before browser hydration. Browser verification exposed a second issue: Next's request URL can contain the internal listener hostname, so a naive redirect switched from 127.0.0.1 to localhost and lost the cookie context. Resolve the actual browser-facing Host or configured/trusted proxy host, preserving the starting origin; cover local and public-proxy cases.
- Callback routing uses Auth-verified, confirmed exact-college users and the existing `profiles.onboarding_complete` flag, not mere row existence. Completed users go to Discover; absent/incomplete profiles go to onboarding. Profile fetch failures preserve a signed-in retry state, rather than overwriting an existing profile through accidental onboarding. Valid sessions recover consumed/expired callbacks without displaying a false login failure. Arbitrary `next` destinations are ignored to prevent callback/login loops.
- Auth restoration and state events resolve user/profile together, gate route rendering while loading, and discard stale requests. The auth-state listener only notifies React; Supabase queries run outside its lock. Auth entry pages and onboarding share a deterministic guard; existing guest views and RLS-backed app data stay on their existing routes.
- Age uses raw string state initialized to `""`, digits-only editing and the mobile numeric keyboard. Empty deletion remains empty; Continue/submission validates an integer >=18 with the existing minimum-age copy, then saves the number. Submission verifies the actual Supabase UUID, removes legacy local/fake-ID/default-age fallbacks, handles failed saves with retry, and preserves server-managed flags.
- No database/provider/ID changes or migration. Google/Supabase branding is an external console setting: preserve the required provider callback, configure GarbaMate name/logo/home/privacy/terms/owned domains and applicable brand verification. A custom auth domain was evaluated but not provisioned; `AUTH_SETUP.md` records the rollout requirements and distinguishes the two callback URLs. Dashboard configuration/live Google consent is not claimed.
- Verification: **59 tests in 12 files**, typecheck, lint and production build pass. The dedicated production-browser suite passes **11 groups** at 360/390/1280px over real PostgreSQL/RLS and HTTPS OAuth/GoTrue fixtures, checking actual S256 challenge/verifier equality, one exchange, new-user completion with numeric 22, existing-user routing/data preservation, refresh/navigation/no onboarding flash, real Chromium restart, cookie refresh, replay/error/profile retry, password and college email magic-link compatibility. Artifacts are `/tmp/omnirush/auth-flow/`; actual hosted Google and native physical-phone behavior remain unverified.

## Search relevance and message receipts — 7 October 2026

- Search ranks the already-loaded authorized profile list in memory: normalized first-name/full-name prefix, another name-word prefix, other name substring, then branch/style/bio. Query and searchable fields use Unicode NFD diacritic removal, trimming, lowercase and collapsed whitespace. Within each tier, a whole-word/phrase match comes first, then the existing `profileScore`, normalized alphabetic name and deterministic final tie breakers. Status is never part of ranking; a nonempty query spans all statuses even when a status tab is selected. UUID/email fields are never matched. The grid retains 30-at-a-time paging and resets pagination when the normalized query changes. Optional highlighting is omitted.
- Search input debounces for 200ms with cleanup cancelling older timers. While the input and committed query differ, the grid shows loading placeholders rather than stale people or an outdated empty message. Ranking is synchronous, so there are no per-query network requests that can race. Existing authoritative profile/status fetches retain their request-generation guard. Empty results say `No one found for 'xyz'. Try a name, branch or style.`
- Migration **014_message_receipts.sql** adds `messages.delivered_at`, the pending-receipt index and default-on `profiles.read_receipts_enabled`. Delivery/read RPCs lock only participant-owned matches, check active status, either-way blocks, real profiles, exact chat generation and timestamp cutoff, and update only the opposite participant's messages. Unmatched/blocked participant calls are quiet no-ops; outsiders are denied. Existing read timestamps are preserved, with no historical-message backfill or epoch changes. Table UPDATE/DELETE and status-column INSERT privileges are denied to ordinary users.
- An app-wide, RLS-filtered message INSERT subscription acknowledges delivery outside the chat, plus initial match loading/focus/visibility and a ten-second reconnect fallback. Open chats subscribe to INSERT **and UPDATE**, retaining the existing three-second checked-message fallback. Updates merge monotonically so a delayed send acknowledgement or poll cannot downgrade read/delivered ticks. The dedicated two-account verification disables that three-second fallback to prove the ticks update through Phoenix events without refreshing the sender.
- Reads require both `document.visibilityState === 'visible'` and incoming-message intersection with the scroll container/window viewport, excluding the mobile bottom-nav area. The client sends the visible IDs through an array overload of `mark_chat_read`; the existing one-argument RPC remains compatible and enforces the same server-side preference/epoch/participant checks. The server cannot attest that an authorized recipient truly looked at pixels; it enforces ownership and opt-out while the UI enforces visibility.
- **Unread/privacy trade-off:** leaving `read_at` null when receipts are disabled conflicts with clearing unread badges using that timestamp alone. A separate `message_seen_private` table records only opt-out recipient views; it has no ordinary-user table privileges and is not added to Realtime publication. Normal unread counts still use `read_at`, subtracting the recipient's private seen rows when needed. `get_chat_unread_counts` and the legacy unread-notification RPC preserve own badges without exposing this state to the sender. Re-enabling receipts can acknowledge previously viewed messages when they are visible again; disabling receipts does not retract acknowledgements already issued.
- Settings persists the receipt boolean with a checked profile update and shows failure feedback. With receipts off the server never sets a new `read_at`, and that user's own stored read messages render grey Delivered ticks. Delivery remains on. There is no online/last-seen addition.
- Every outgoing bubble and own last-message chat preview uses the shared accessible status component: clock Sending, grey single Sent, grey double Delivered, cyan double Read, or a red failure/retry action. Each icon has a title/accessible state label. Outgoing bubbles use a darker pink-to-brown gradient (`#55214b` → `#573027`); tests check cyan `#34B7F1` and grey `#b6bccb` at >=4.5:1 across gradient samples. Consecutive same-sender messages within five minutes have tighter spacing, retaining a tick on every own message.
- Sends now use `send_chat_message` with a stable client-generated message UUID and the current epoch. Optimistic pending/failed rows stay in the chat and retry with the same UUID. The RPC returns the existing immutable matching row after a lost acknowledgement, and rejects mismatched identity/body/epoch reuse. This adds one narrow send RPC to prevent retry duplicates even when an INSERT committed before a network failure. Pending/failed rows are in-memory only and reset on navigation; no offline outbox is introduced.
- Verified on the production build: TypeScript, lint, **35 tests/10 files**, migration 014 applied twice, real SQL receipt/privilege/opt-out/unread/epoch/block/retry checks, the original unmatch/health/auth/status SQL suites, five dedicated search/receipt browser groups, seven mobile-polish groups, seven follow-up groups, 21 UI checks and five auth groups. The legacy UI fixture now reloads before injecting its pre-pass like and waits for flight settlement before Undo; its clearance check scrolls in-flow actions past the fixed nav. Artifacts and commands are in `TESTING.md`. Supabase HTTP/Auth/Phoenix are emulated over real local PostgreSQL; hosted Realtime/Auth and physical-device/Safari behavior remain unverified.

## Initial assumptions

- The app uses a current stable Next.js App Router setup with the project package versions pinned in `package.json`.
- Supabase environment variables are optional for the local UI shell so the app can render and run unit tests without credentials; authenticated/data operations fail closed with a friendly message until configured.
- Festival name and nine availability nights are isolated in `config/festival.ts`. The countdown start date was removed in the health cleanup.
- Email prefix suggestions recognize `cs`, `is`, `ec`, `ee`, `me`, `cv`, `ai`, and `ad`; unknown codes remain blank. `cs` maps to CSE, `is` to ISE, `ec` to ECE, `ee` to EEE, `me` to ME, `cv` to CV, `ai` to AI&ML, and `ad` to AI&DS.
- Academic year prefill treats an admission year as first year in that academic cycle and derives a 1st–4th year suggestion relative to the current academic year; users may always change it.
- Demo data is disabled by default and is available only through explicit seed commands and an environment flag.
- The initial MVP uses server actions and typed Supabase queries rather than a separate API service. Realtime subscriptions are added in the chat phase.
- Where live Supabase credentials or OAuth providers are unavailable in this workspace, the implementation will include migrations, tests, and clear setup instructions rather than claiming external verification.

## October 2026 Discover follow-ups

- Production (`next build` + `next start`) is the performance target. Real-phone GPU performance cannot be inferred from CPU throttling alone. Diagnose on a phone with `/discover?debug=fps`; this explicit diagnostic opt-in is available in production as well as development, otherwise the meter runs no frame loop.
- Discover has no ambient CSS animation, including the Vibe pulse and notification/nav pulses. Remaining animations pause through root `data-dragging`/`data-tutorial` flags. Explicit user-action animation and tutorial demonstrations remain enabled, subject to reduced motion.
- The top card uses pointer capture and one requestAnimationFrame transform write (`translate3d`), not Framer Motion's drag recognizer/motion-value transform pipeline. Framer Motion still scales the next card; WAAPI handles flight/settling. The imperative `flyOff` API is unchanged. This removes avoidable drag scheduling overhead without changing the gesture projection or action semantics.
- Images from existing supported origins (including Supabase Storage) go through Next's optimizer with a maximum 800px rendition, WebP preferred over AVIF for predictable decode cost, and responsive `sizes`. The next two optimized resources are explicitly decoded; promotion also waits for the warmed resource. Data/blob/legacy unknown origins preserve their previous URL contract, so resizing arbitrary unknown origins is not guaranteed. No unrestricted image proxy was introduced.
- Each page load and Shuffle gets a new in-memory seed. SQL calculates independent per-profile `-ln(u)/(0.35+score/100)` keys salted by the authenticated user. Seed + keyset cursor accompany every page request. The UI keeps a session snapshot and preserves surviving order on refetch, so exclusions cannot shift an index and skip candidates.
- One in eight snapshot positions is reserved for the lower-scoring third when the pool is large enough. This deterministic exploration mix follows the weighted shuffle, with no duplicates. A returning unmatched profile is inserted at a seeded random position among remaining candidates. Separate seeds are independent; an identical short sequence by chance is mathematically possible, especially for tiny pools.
- The current client materializes the paginated candidate snapshot in memory rather than introducing a new server-side feed-session store. This fits the existing college-scale client architecture and ensures a stable session. A large campus deployment may later need incremental snapshot storage without changing ranking semantics.
- `RelationshipsProvider` is the sole active-match cache for Discover, Matches, Chats, and profiles. Realtime match updates, local events, focus refresh, and authoritative refetch drive it. Empty remote results stay empty; local cache rows cannot resurrect a remote unmatched pair. Counts derive from this cache. This app had no unread-message counter; unmatched chats are excluded from all chat/message queries rather than adding an unrelated unread feature.
- Unmatch is a participant-only transaction. Repeated confirmed calls on an already-unmatched row are safe no-ops, resolving the request's idempotency requirement. Non-participants and unauthenticated callers still fail. Pair advisory locks serialize like/unmatch; message row locks and a chat-generation token handle delayed sends and re-matches.
- Only `like_user` may create/reactivate remote matches. Older broad match INSERT/UPDATE policies are removed. Old message evidence remains stored and accessible only to existing admins through a reported-pair evidence RPC. Neither ordinary message RLS nor block rules are weakened.
- Tutorial completion/Skip calls an owner-scoped RPC for the profile flag. Demo profiles exist only in the lazy tutorial chunk and local practice state. They never enter the real feed or mutation/quota callbacks. Rendering/lazy-load failures close the tutorial; a failed flag save permits use of the app and retries on a later visit.
- Apply `008_unmatch_tutorial.sql` followed by `009_seeded_discovery.sql` with the UI deployment. Older open clients omit the chat-generation token and must reload to send under the hardened message rules. Authentication providers, session handling, routes, and the existing Vibe quota implementation are unchanged.
- SQL and browser integration verification use a disposable local PostgreSQL database with test-only Supabase role/auth helpers. Browser requests execute the actual migrations/RPCs/RLS; the Supabase HTTP and Phoenix/Realtime transports are emulated. This does not claim verification against the deployed Supabase service or a physical phone.
- Message RLS uses the security-definer pair-exclusion helper instead of reading private block rows directly, so a block made by either participant hides the conversation from both. The helper reveals only the current user's excluded partner IDs. SQL tests verify this while the match remains active and deny non-admin evidence access.
- A match celebration is invalidated by an explicit inactive-match event, rather than treating a pending cache refresh as proof of unmatch. Tutorial automatic-open listeners recheck the already-shown guard at invocation time; demo-card unmount events cannot reopen the sheet after Skip/Esc.
- Final production verification passed the SQL integration, both browser suites, TypeScript, lint, build, and 29 discovered unit tests. The photographic 32-swipe DPR-2/4×-CPU run verified stable surviving order, reported rounded 60 movement FPS and no card drag renders, with 12 estimated missed frames over the full meter observation. Unmatch passed from Matches, chat, profile and Discover. The original active-drag trace measured approximately 60 FPS / 16.7ms p95. Exact scope, artifacts and unverified failure/device cases are recorded in `DESIGN_NOTES.md`.

## Health check and cleanup — October 2026

- Reproduced the post-merge production Discover failure against real local PostgreSQL RPCs/RLS with emulated Supabase HTTP/Phoenix transport: `cannot add postgres_changes callbacks for realtime:active-matches:<user> after subscribe()`. Both the shared provider and expanded notification component requested the same Supabase topic, which returns an already-subscribed channel. Every subscription owner now has a unique topic. A regression test models the shared-topic failure, and the production browser driver keeps simultaneous provider/notification subscribers active without page errors. This identifies a real reproduced code fault; no deployment URL or host error logs were available to prove that every deployed error has that cause.
- Error boundaries log reference/message/stack/digest/route to the browser console. The global boundary covers root-layout errors; Next's `onRequestError` logs the same fields for server errors without query-string tokens. Users normally see only a friendly message and reference; development or `?debug=1` enables the actual message. Profile collections and images are normalized at the data boundary; invalid rows are logged/skipped, nullable optional fields become safe defaults, and internal/legacy fields are discarded.
- No live service-role key or authenticated live session was available. The historical source project was reachable with its public anon key: the read-only public-names RPC returned six first-name rows, none containing demo markers, and still included UUID `id` fields. Anonymous probes confirmed `discover_feed` and `discovery_blocked_ids` exist and deny anon execution, and the match epoch columns are queryable through the REST schema. This is a limited public API smoke check, not a full demo/auth/storage audit or verification of the deployment host's configured project.
- Source audit found exactly 30 hard-coded `bms-<USN-like>` records (20 women, 10 men), all `is_demo=false`, all with stock-person-photo URLs, automatically added by `db.getProfiles` and browser-cache initialization. The old seed/clear scripts were placeholders and migrations 001–009 do not insert that catalog. The initial disposable database audit returned 180 test profiles and zero flagged/prefixed demos; those counts are not production counts. `supabase/audit-health.sql` and `npm run audit:data` provide the privileged live audit without printing individual emails/USNs.
- Remove all countdown UI and dead start-date code; retain the festival name and Day 1–9 availability configuration. Landing preview cards are decorative illustrations, not discoverable accounts. Tutorial cards are labelled Practice, never verified, and never touch likes/matches/quota callbacks.
- Samples are auth-linked because the existing profile FK requires it. Use the local Admin API script, never raw SQL inserts into `auth.users`. It reserves 30 internal `.invalid` addresses, supplies trusted `app_metadata.is_sample`, bans sign-in, and reuses existing marked accounts by address. Ordinary signup cannot supply trusted app metadata. Rerunning sequentially reuses the same IDs; address collisions with unmarked accounts fail rather than overwrite. The seeder uses stable, distinct emoji avatars and varied plausible ages/years/nights; no photographs or student identifiers.
- `is_sample` is a database-only column and is excluded from ordinary SELECT grants and RPC projections. `is_verified` is server-derived only from a confirmed exact `@bmsce.ac.in` email and never true for a sample; clients cannot edit it. Cards/details/profiles/chats render badges only when this trusted boolean is true. UUIDs remain technical relationship keys in requests/routes, never visible labels or search fields; removing those keys from all requests would make matching/reporting impossible.
- The database `SHOW_SAMPLE_PROFILES` setting defaults true and is authoritative for RLS/feed visibility. `SHOW_SAMPLE_PROFILES=false` in the seeder environment sets it false. One-line SQL can hide every sample; the removal command uses marked Admin API identities and cascades profile relationships. `like_user` records a sample like but exits before mutual-match creation. A match trigger rejects sample pairs even for direct writes; the message guard rejects them too. Notifications and admin/account aggregates exclude samples. Sample filtering respects age, mutual preferences, block/hidden state and seeded ordering.
- `010_health_samples.sql` is the single idempotent repair after 001–009. It reasserts the 008/009 signatures and chat-generation rules, adds sample/verification/settings/unread support, and replaces all policies on the app tables, including any `allow_all_*` policies generated by the old admin UI. It enables RLS and refreshes PostgREST. It does not delete real accounts or conversations. Public-name responses become name-only. New frontend must be released after this repair.
- SQL cannot safely remove physical Storage blobs. Cleanup is a transaction restricted to existing profile `is_demo`, prefixed IDs, or trusted admin metadata. It queues only owned Storage paths, removes demo relationships, and defers auth/profile deletion while queued blobs remain. Run the Storage API cleanup then rerun SQL to finish. This preserves Storage metadata until blob deletion succeeds and is safe to retry. Real-user names, USNs, domains, and user-editable metadata alone are never deletion criteria.
- Remove the old local-password/session authentication and exposed admin-passkey controls; they were not real authentication. Only Supabase-confirmed college accounts authenticate; admin access requires `admin_users` membership. Auth callbacks use validated Supabase users and same-origin redirect targets. Admin moderation/report writes are checked against RLS, with no fake test results or fabricated audit entries.
- Notifications now derive from authorized active real chat rows, with actual unread-message counts and owner-scoped read RPCs. Unmatch/block/old epochs cannot retain unread entries. A visible-tab five-second authoritative relationship refresh handles a block hiding its update from Realtime's own RLS checks. Pass retains incoming likes so Undo never needs to impersonate their sender; all failed remote writes propagate instead of inventing local success.
- Message reads/unread/read-receipt operations also require exact chat-generation equality, not just a timestamp cutoff, so a postdated old row cannot resurface on rematch. Original-epoch legacy rows are backfilled; unassignable null-generation rows from already-reactivated conversations remain admin evidence only. The SQL rematch regression deliberately postdates an old message to 2099. Defensive pagination also keeps valid rows when a corrupt final profile prevents using the last cursor.
- Relationship status is now a server-authoritative `discover_relationships()` result with precedence matched → sent → passed → incoming → new. `set_decision` serializes pairwise pass/interest transitions, preserves incoming likes, withdraws only the actor's interest, checks persisted same-day Vibes against the existing limit, and records recipient notifications. Sent/Passed/Matches are grids; Explore and Explore search use the same status rows. Source diagnosis identified an idempotent decision/source-list mutation issue behind the prior Passed freeze; the rendered stack explicitly removes the decided ID even when the database status remains unchanged. The helper has a regression test; a pre-fix browser reproduction was not captured.
- Notification events are recipient-owned and realtime-scoped. Interest withdrawal, pass, block and report create no event; stale interest events are filtered/deleted. Glass blur is reserved for notification/tutorial overlays with solid and reduced-transparency fallbacks; profile cards and grids remain unblurred. The optional browser push path is intentionally deferred.
- Public URL/anon key must be configured before building; no embedded default project/key remains. Service-role key is used only by local seed/audit scripts and ignored `.env.samples`. Build validation rejects `sb_secret_*` or service-role JWTs in the public anon-key variable. Current source and built browser bundles were searched; no embedded service key/admin passkey was found. The Supabase SDK itself contains a literal `sb_secret_` prefix check, which is not a credential.
- Vitest is scoped to `tests/` so untracked `.kilo` worktree copies are not mistaken for independent application tests. All existing application test files are retained. Exact final checks, deployment order, local transport limitations and artifacts are in `HEALTH_CHECK.md`.
